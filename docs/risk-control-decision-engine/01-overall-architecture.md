## 1. 系统定位与核心矛盾

风控决策引擎的本质是：**在毫秒级延迟内，对一个事件（交易、登录、注册、提现等）执行一组可动态配置的规则/模型，输出决策（放行 / 拦截 / 人工审核 / 加验）**。

设计的核心矛盾有三个，整个架构围绕它们展开：

1. **低延迟 vs 特征丰富度** —— 支付场景通常要求 P99 < 100ms，但好的决策需要大量实时聚合特征；
2. **策略迭代速度 vs 稳定性** —— 风控策略每天都在变，但引擎不能因为改规则而发布代码；
3. **实时对抗 vs 事后可解释** —— 每一个拦截都可能被申诉，必须能完整回放"当时为什么这么判"。

## 2. 总体架构

```
业务系统
   │  同步调用 (RPC/HTTP)
   ▼
┌─────────────────────────────────────────────┐
│ 接入层：鉴权、限流、字段校验、事件标准化       │
├─────────────────────────────────────────────┤
│ 决策核心（同步链路）                          │
│   1. 名单服务（黑/白/灰名单，最先执行）        │
│   2. 特征平台（实时+离线特征取数）             │
│   3. 规则引擎（DSL/决策表/决策树）             │
│   4. 模型服务（评分卡/GBDT/深度模型）          │
│   5. 决策仲裁（多策略结果合并出最终动作）       │
├─────────────────────────────────────────────┤
│ 异步链路：事件落库 → Kafka → Flink 实时指标    │
│           → 案件中心 / 人审 / 离线分析         │
├─────────────────────────────────────────────┤
│ 管理面：策略管理后台、灰度/AB、回测、监控大盘   │
└─────────────────────────────────────────────┘
```

## 3. 核心模块设计

### 3.1 事件接入与标准化

- 定义统一事件模型（Event Schema）：事件类型、主体（用户/设备/卡/商户）、上下文（IP、设备指纹、金额、时间）。用 schema registry 管理版本，业务方接入只做字段映射。详见 [02-unified-event-model.md](./02-unified-event-model.md)。
- 同步接口必须有**兜底策略**：超时或引擎故障时按事件类型配置默认动作（如登录默认放行、大额提现默认转人审）。风控挂了不能拖垮交易主链路，这是接入层最重要的契约。

### 3.2 特征平台（最难也最值钱的部分）

特征分三层，取数路径不同：

| 类型 | 例子 | 存储/计算 |
|---|---|---|
| 事件原始特征 | 本次金额、IP、设备号 | 请求体直接携带 |
| 实时聚合特征 | 该卡近1小时交易笔数、近5分钟异地登录次数 | Flink 滑动窗口 → Redis/HBase |
| 离线画像特征 | 用户历史逾期率、设备关联账户数、图特征 | 离线数仓 T+1 批算 → KV 存储 |

关键设计点：

- **特征注册中心**：每个特征有唯一 ID、口径定义、负责人、上下游血缘。规则引用特征只认 ID，避免"同名不同口径"——这是风控团队最经典的事故来源。
- **实时/离线口径一致性**：同一个特征的流式计算和批式回补必须用同一份定义生成（Flink SQL 与离线 SQL 同源），否则回测结果和线上表现会对不上。
- **取数并行化 + 分级超时**：特征分"必要/可选"，可选特征超时就用默认值降级，不阻塞决策。

### 3.3 规则引擎

- **不让策略人员写代码**。提供受限 DSL 或表达式语言（类似 Aviator/QLExpress 的表达能力），加上可视化的决策表和决策树编辑器。规则示例：

  ```
  amount > 5000 && card_tx_count_1h >= 3 && ip_city != last_login_city → REVIEW
  ```

- 规则编译成执行计划后缓存；热更新走"版本发布"而不是逐条改：策略人员编辑 → 静态校验（引用的特征是否存在、类型是否匹配）→ 回测 → 审批 → 灰度 → 全量。每个版本不可变、可一键回滚。
- 规则组织成**策略集（Policy）**，按事件类型路由；集合内支持短路（命中拦截即返回）与全量执行（用于观察模式）两种执行模式。
- 每条新规则先跑**影子模式（shadow）**：只记录命中不产生动作，观察命中率和误伤率达标后再转正。这是防止"一条烂规则拦掉全站交易"的核心机制。

### 3.4 模型服务

- 规则负责"快速响应已知模式"，模型负责"泛化未知风险"，两者互补而不是二选一。
- 模型独立部署成打分服务，规则引擎把模型分当作一个普通特征使用（`fraud_score > 0.85 → DENY`），模型升级与策略调整解耦。
- 模型上线走 champion/challenger：新模型旁路打分一段时间，对比 KS/AUC 与线上误伤，再切流量。

### 3.5 决策仲裁与动作

- 多条规则/多个模型可能给出冲突结论，需要仲裁层：通常按动作严重程度取最严（DENY > REVIEW > CHALLENGE > PASS），并支持白名单一票放行、监管名单一票否决的优先级例外。
- 输出不只是动作，还要带**决策依据**：命中的规则 ID、关键特征取值、模型分。这是可解释性和申诉处理的基础。

### 3.6 数据闭环

- 每次决策的完整快照（输入事件、所有特征值、命中规则、最终动作）异步落到 OLAP（ClickHouse/Doris 一类），支持任意决策的**完整回放**。
- 人审结论、用户申诉、事后确认的欺诈标签回流到数仓，作为模型训练样本和规则效果评估的 ground truth。**没有标签回流的风控系统无法迭代**，这个闭环要在第一期就建，不能后补。

## 4. 非功能性设计

- **延迟预算**：同步链路整体 P99 < 100ms 的话，大致分配：接入 5ms、名单 5ms、特征取数 40ms（并行）、规则+模型 30ms、留余量 20ms。特征取数是大头，KV 存储选型和并行取数框架值得重点投入。
- **可用性**：引擎无状态、多机房部署；名单和热点特征本地缓存兜底；全链路压测覆盖大促流量。
- **监控**：除系统指标外，更重要的是**业务指标监控**——每条规则的命中率突变告警（命中率暴涨往往意味着误伤或攻击，暴跌意味着规则失效或特征断流）、特征覆盖率/空值率告警。
- **合规审计**：策略变更全程留痕（谁、何时、改了什么、审批人），决策快照保留满足监管要求的期限。

## 5. 演进路径

不建议一上来就建全套，合理的分期：

| 阶段 | 内容 | 目标 |
|---|---|---|
| 一期 | 名单 + 硬编码少量规则 + 决策快照落库 | 先挡住最明显的坏人，先有数据 |
| 二期 | 规则 DSL + 管理后台 + 影子模式 + 实时特征（Flink） | 策略迭代不再依赖发版 |
| 三期 | 模型服务 + 回测平台 + 标签闭环 | 从"专家经验"走向"数据驱动" |
| 四期 | 图计算（团伙挖掘）、设备指纹深化、跨事件序列建模 | 对抗团伙化、专业化的欺诈 |
