# 风控决策引擎系统设计 · 特征平台

> 系列文档：[01-总体架构](./01-overall-architecture.md) · [02-统一事件模型](./02-unified-event-model.md) · 03-特征平台（本文）
>
> 特征平台的职责：**把"口径定义"变成"决策时刻毫秒级可取的数值"**，覆盖特征从定义、计算、存储、服务到质量监控的全生命周期。

## 1. 定位与职责边界

- 特征平台**不做决策**——规则引擎只管"拿特征值来判断"，不关心值怎么算出来的；
- 特征平台**不定义业务口径的对错**——口径由策略/算法人员在注册中心声明，平台保证"声明什么就算什么，实时离线算得一样"。

## 2. 特征分类

不同类别的特征走不同的计算与存储路径：

| 类别 | 例子 | 计算方式 | 取数路径 |
|---|---|---|---|
| 事件原始特征 | 本次金额、IP、渠道 | 无需计算 | 请求体直接取 |
| 实时聚合特征 | 该卡近1h交易笔数、近5min失败次数 | Flink 滑动/滚动窗口 | Redis（热） |
| 离线画像特征 | 用户历史逾期率、账龄、常用登录城市 | 数仓 T+1 批算 | KV 存储（HBase/自研） |
| 图/关系特征 | 设备关联账户数、二度关联黑名单数 | 图计算引擎批算 + 近线增量 | KV 存储 |
| 三方外部特征 | 运营商核验、征信分 | 外部 API | 实时调用 + 结果缓存 |
| 衍生特征 | 本次金额 / 该用户近30天均值 | 决策时刻现场计算 | 引擎内表达式求值 |

分类的意义：**规则作者不需要知道这些差别**——他引用的都是一个特征 ID，取数路径由平台按注册信息路由。

## 3. 总体架构：五层

```
┌────────────────────────────────────────────────┐
│ ① 定义层：特征注册中心（元数据 + 口径 DSL）        │
├────────────────────────────────────────────────┤
│ ② 计算层：Flink 流计算 ←同一份口径定义→ 离线批计算  │
├────────────────────────────────────────────────┤
│ ③ 存储层：Redis(热) / HBase(温) / 数仓(冷+回测)    │
├────────────────────────────────────────────────┤
│ ④ 服务层：Feature Serving（批量取数、并行、降级）   │
├────────────────────────────────────────────────┤
│ ⑤ 质量层：覆盖率/空值率/分布漂移/断流监控           │
└────────────────────────────────────────────────┘
```

## 4. 定义层：特征注册中心

每个特征是一条受管元数据，核心字段：

- `feature_id`（全局唯一，规则只认它）、名称、中文描述、owner；
- **主体维度**：绑定到统一事件模型的 `(entity_type, role)`，如"卡维度""设备维度"——这是事件模型里 entities 设计的回报：任何实体维度的聚合都是同一套框架；
- **口径定义（声明式）**：源事件类型 + 过滤条件 + 聚合函数 + 窗口，例如：

  ```yaml
  feature_id: card_tx_cnt_1h
  entity: card            # 聚合主体
  source_events: [payment.card_charge]
  filter: payload.status != 'FAILED'
  agg: COUNT
  window: { type: sliding, size: 1h, slide: 1m }
  default: 0              # 取不到时的降级值
  ttl: 2h
  ```

- 类型与值域、默认值、TTL、上线状态（开发/影子/上线/下线）、血缘（哪些规则和模型在用——**下线前必查引用**）。

关键原则：**口径是声明的，不是代码**。声明式定义由平台编译成 Flink 作业和离线 SQL 两种产物，这是实时/离线一致性的根基——两边永远同源，不存在"两个人分别实现同一个口径"这回事。

## 5. 计算层

### 5.1 流式计算（Flink）

- 按声明编译成聚合作业。
- **分桶预聚合**：精确滑动窗口成本高，通用做法是按分钟粒度存桶（如 `card:c1:tx_cnt` 的 60 个分钟桶），查询时合并最近 60 个桶——精度损失一分钟以内，换来存储和计算量大幅下降。"近30天"这类长窗口用天级桶 + 当天实时桶合并。

### 5.2 离线批计算

同一份声明编译成离线 SQL，两个用途：

1. 计算 T+1 画像特征；
2. **回补（backfill）**——新上一个"近30天"特征不用等30天，用历史事件批算出初始值灌入 KV，流作业从当前时点接力。

### 5.3 去重与乱序

- 以 `event_id` 幂等去重；
- 以 `received_at` 为时间基准（客户端时间不可信）；
- 允许小窗口乱序（watermark），迟到太久的事件只进离线不修实时。

## 6. 存储层

- **Key 设计**：`{entity_type}:{entity_id}:{feature_id}`（分桶特征再加桶后缀），所有维度统一编址。
- **冷热分层**：
  - 热特征（高频、短窗口）→ Redis，TTL 略大于窗口长度自动过期；
  - 画像类 → HBase/持久 KV；
  - 数仓保留每日特征快照——这是回测做 **point-in-time join** 的物料。回测必须用"事发当时"的特征值，用今天的值回测历史事件是最常见的作弊性错误。
- 决策快照里已记录当次用到的所有特征值，线上排查不依赖存储回溯，直接看快照。

## 7. 服务层：Feature Serving

决策链路上的取数接口，设计要点：

1. **批量 + 并行**：引擎按策略集分析出本次需要的全部特征，一次请求批量下发；服务端按存储介质分组并行取数（Redis 一批 pipeline、HBase 一批、三方一批）。
2. **分级超时与降级**：每个特征在注册时标注"必要/可选"。可选特征超时 → 用注册的默认值，并在决策快照里标记"降级"；必要特征超时 → 按事件类型的兜底策略走（转人审/放行）。**降级必须可观测**：降级率是核心告警指标，否则风控会在"特征大面积拿不到、规则全在用默认值"的状态下裸奔而无人察觉。
3. **三方特征的成本控制**：先查缓存，未命中再调外部；支持"条件触发"——只有前置规则命中灰名单时才花钱调征信，避免全量调用。
4. **衍生特征**在服务层或引擎内做轻量表达式计算，不落存储。

## 8. 质量层

- **断流告警**：某特征对应的源事件流量归零 → 立即告警（往往是上游改字段/掉线，特征会静默退化为默认值）；
- **覆盖率/空值率**：按特征统计取数成功率、非默认值占比，突变告警；
- **分布漂移**：数值特征做日级 PSI 监控，漂移大要么是攻击、要么是口径被上游改坏了——两者都必须有人看。

## 9. 演进节奏

- 一期：注册中心 + Redis 计数器 + 手写少量 Flink 作业；
- 二三期：声明式编译、回补、point-in-time 快照；
- 最后：图特征。

**先保证"一个特征一个口径一个 owner"的治理纪律，再谈平台化**——治理没立住的情况下上平台，只是把混乱自动化了。

## 10. 消费信贷特征契约补充（新增）

遵循 [02 第6.5节与第7节](./02-unified-event-model.md#65-时点计数与回放)。FeatureSet 除值外携带状态、口径版本、as_of、available_at 和来源；真实零值与缺失、超时、过期分离。默认值必须保留降级标记，不得把未查询征信解释为无负债。

received_at 继续用于默认行为窗口；可信账务时间轴须显式注册并受首次可用时间约束。申请、决策、放款分别计数，声明是否包含当前事件且恰好一次。客户、授信账户、借据维度不能混算。

编排负责合并每阶段规则与模型的特征依赖；Feature Serving 执行批量取数，规则求值器不自行发 RPC。条件外数调用须经显式阶段和权限校验，具体触发与缓存期限待审批。回放使用固化快照或 point-in-time 数据，不覆盖生产特征、不重查外数。


第 [02 §9](./02-unified-event-model.md#9-契约验收与审计可靠性新增) 节补充验收要求：源快照需校验归属、新鲜度及版本；特征窗口明确业务时点与首次可见时间，冲正与迟到处理受口径版本管理。真实零值、缺失和降级分别留痕。每日快照不能还原日内变化时，依赖增量版本或当次决策快照，不能声称仅凭 T+1 数据精确复现。
