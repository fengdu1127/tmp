# 风控决策引擎系统设计 · 规则引擎

> 系列文档：[01-总体架构](./01-overall-architecture.md) · [02-统一事件模型](./02-unified-event-model.md) · [03-特征平台](./03-feature-platform.md) · 04-规则引擎（本文）

## 1. 定位与概念模型

规则引擎做一件事：**对"事件 + 特征"求值一组条件表达式，产出动作**。它不取数（特征平台的事）、不做最终裁决（仲裁层的事）、不管理规则生命周期（管理后台的事）——引擎本身只是一个高性能求值器，复杂度都放在编译期和管理面。

概念模型三层：

```
Policy（策略集）—— 按 event_type 路由，如 "payment.card_charge 主策略集"
  └── RuleGroup（规则组）—— 组织与执行顺序：名单组 → 高危拦截组 → 累计限额组 → 观察组
        └── Rule（规则）—— 条件 + 动作 + 元数据
```

一条规则的完整定义：

```yaml
rule_id: R20260819_001
name: 高危异地大额交易
status: shadow            # draft / shadow / active / offline
priority: 100             # 组内执行顺序
condition: >
  amount.value > 500000
  && card_tx_cnt_1h >= 3
  && ip_geo.city != user_common_city
action: REVIEW
action_params: { queue: "high_risk", expire_hours: 2 }
valid_period: [2026-08-19, null]   # 支持活动期临时规则自动过期
owner: zhangsan
```

## 2. DSL 设计：能力要克制

策略人员用的表达式语言，**表达能力必须是受限的**——这是安全性和性能的来源。

**有的**：

- 算术 / 比较 / 逻辑运算、三元表达式；
- 类型系统（数值 / 字符串 / 布尔 / 时间 / 集合，静态检查）；
- 内置函数库：时间差、字符串处理、`in_list('黑名单IP', ip)` 名单查询、正则、地理距离；
- 引用事件字段（`payload.amount`）和特征（直接写 `feature_id`）。

**没有的**：

- 循环、自定义函数、IO、任意对象方法调用。

表达式必然在微秒级结束，不可能写出死循环或把引擎打挂的规则。

同一套底层表达式之上提供三种编辑形态，适配不同人群：

| 形态 | 适用人群 / 场景 |
|---|---|
| 表达式 | 高级策略人员，灵活组合 |
| 决策表 | 运营批量配置（金额区间 × 用户等级 → 动作） |
| 决策树 | 可视化分支逻辑 |

三种形态都编译到同一个中间表示（IR），执行层只认一种东西。

## 3. 编译与执行

发布时编译，运行时零解析：

```
DSL 文本 → 词法/语法分析 → AST
  → 静态校验：引用的特征是否已注册？类型是否匹配？函数参数是否合法？
  → 特征依赖分析：提取本策略集引用的全部 feature_id 集合
  → 编译成执行计划（策略集粒度），缓存
```

两个关键设计：

1. **特征依赖前置**：编译期就算出"这个策略集需要哪些特征"，请求进来时一次性批量取数（对接特征平台的批量接口），然后纯内存求值。绝不允许"执行到某条规则才发现要取数"——那会把取数打散成串行 RPC，延迟直接失控。
2. **公共子表达式共享**：几百条规则里 `amount.value > 100000` 可能出现几十次，编译期做子表达式去重，同一请求内只算一次。规则量极大时可以上 Rete 类网络，但多数场景下"批量取数 + 子表达式缓存 + 顺序求值"已经足够快，不要过早引入 Rete 的复杂度。

执行模式按规则组配置：

- **短路模式**：命中 DENY 即停，用于拦截组；
- **全量模式**：所有规则都算完，用于观察组和需要完整命中清单的场景。

影子规则永远全量执行、只记录不出动作。

## 4. 发布流水线（比引擎本身更重要）

规则错一条可能拦掉全站交易，发布流程是刚性的：

```
编辑 → 静态校验 → 样例测试 → 回测 → 审批 → 影子/灰度 → 全量
```

- **样例测试**：每条规则要求附带正反测试用例（这个事件应命中/不应命中），改规则时自动回归——相当于规则的单元测试。
- **回测**：新版本在历史决策快照上重放（point-in-time 特征），输出命中量、与老版本的决策差异（多拦了谁、放了谁）、预估误伤率。回测报告是审批的必要材料。
- **审批**：修改人 ≠ 审批人，高危动作（DENY 类）双人审批，全程留痕。
- **影子期**：新规则以 shadow 状态上线，跑够量后看实际命中率与预期是否一致，再转 active。
- **版本不可变**：发布的是策略集的一个完整版本快照（内容寻址），回滚 = 切回旧版本指针，秒级生效。决策快照里记录版本号，任何历史决策可精确复现当时的规则集。

## 5. 运行时热更新

- 管理后台发布新版本 → 写配置中心 → 引擎实例监听变更，拉取并**编译校验通过后**做双 buffer 原子切换（新请求走新版本，在途请求跑完旧版本）；
- 编译失败则保持旧版本并告警，坏配置永远上不了线；
- 集群内版本收敛监控：所有实例应在秒级收敛到同一版本，长期不一致要告警（否则同一个用户重试两次可能得到不同决策）。

## 6. 可观测性与规则治理

每条规则是一个监控对象：

- 命中率（突涨 = 误伤或攻击，归零 = 失效或特征断流）；
- 影子规则的"假想命中率"；
- 规则求值耗时 TopN。

管理面配套**规则治理**：定期报表列出连续 90 天零命中、与其他规则完全重叠、owner 已离职的规则，推动下线——规则库只进不出的话，两年后没人敢动任何一条。

## 7. 避坑清单

1. **不要让规则之间产生隐式依赖**（规则 A 的动作影响规则 B 的条件）。需要编排就显式用规则组顺序表达，否则执行顺序一变结果就变，没人能推理。
2. **不要在 DSL 里开"执行任意脚本"的后门**（Groovy 脚本规则是常见诱惑）。一旦开了，安全审计、性能保证、静态校验全部作废，而且再也关不掉。
3. **决策表/树不要和表达式规则各自实现执行器**，必须归一到同一 IR，否则两套语义会慢慢分叉。

## 8. 消费信贷规则输入输出补充（新增）

遵循 [02 第7节模块契约](./02-unified-event-model.md#7-消费信贷模块输入输出与边界新增)。编译期同时登记事件字段、特征及模型输出依赖；模型分以受控引用进入规则上下文，并保留模型与预处理版本。依赖模型分的规则在模型完成后执行，失败或缺失显式走场景兜底，不填成低风险分。

规则输出为候选动作、参数、原因码及执行状态；最终授信额度、支用条件和贷中动作由已发布策略编排与仲裁生成。规则不可直接变更账户或放款。贷中多动作按目标和参数处理冲突，不能只取最严动作。短路未执行的规则标记 SKIPPED，不能记为未命中；影子结果不进入生产仲裁或业务执行。
